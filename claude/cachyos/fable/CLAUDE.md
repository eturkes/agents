## Reading

- Whole files → `Read`; shell inspection → bounded queries. Reader permissions allow `Read` while gating pagers, colorizers + TTY editors in Bash; preserve that separation.
- `@path` attaches a mention-time snapshot; `@path#L10-20` selects lines. Missing/oversize attachments can be silent → verify file presence + read explicitly.
- Binary-contained text → `/usr/bin/rg -a -o '<pat>.{0,400}'`; widen context for minified call sites.
- Structured-file edits → verify disk bytes + entry counts (`wc -c`, `jq`), inspect indexed entries, then use anchored edits. Treat count mismatches as partial views; inspect diff churn before accepting a rewrite.
- Context → `context-gauge`; transcript → `context-gauge -p`; where `usage.iterations` lists passes (compaction), occupancy = the last executor pass. MAIN = `claude-fable-5-2` at 1M → 967K; teammates = GPT at 870K → 837K; gauge 100% = compaction trigger, pending payload can trigger earlier.

## Delivery

- Before ending a turn, check the last paragraph: a plan, an analysis, a list of next steps or a promise about undone work → do that work now with tool calls, retries after errors + gathering missing information included; steps that wait on work in flight (background shell, `Monitor`, teammate) stay named + the turn ends on that wait (`Background waits`); a question → `AskUserQuestion` where my input decides, else the work it asks about. A long context or session → keep working. Before a command that changes system state (restart, delete, config edit), check that the evidence supports that specific action: a signal that pattern-matches a known failure can have another cause.
- Messages to me (status notes, turn reports, final message, questions) = human-facing; goal = a human understands each on first read. Reader = technically proficient + low-context: your tool calls, reasoning + files stay unseen, and I may switch in from other work ⇒ each message stands alone. Key points in the opening sentences, detail after; each reference + idea explained where it first appears; a term or abbreviation coined during the work → say what the thing is. Plain words in full sentences, ASD-STE100 style: short sentences, one idea each, active voice, the same word for the same thing. Prose where ideas connect, bullets for separate items; this file's shorthand (`→`, `=`, `+`, fragments) stays in agent-read text. Content = blockers + essentials with the context they need; the rest on request.
- Notify set = `.agent/spec.md` `Intent`, every `CLAUDE*.md` + each file `~/.local/app/agents` tracks or deploys. Launch dir outside that repo → MAIN's final message, pause included, names each notify-set edit + its change, from a `notify-scan` run.
- Per response: private list of what's needed next → one batch of every item whose inputs are in hand; items awaiting another's result → the next response.
- Scope = every requested behavior, complete. What else a change takes in + how it is tested = the project's `CLAUDE.md` where one rules it (project template: `Collaboration` ownership, `Engineering` units + tests). Elsewhere: mid-task find (pre-existing bug, perf concern, unmentioned behavior) → follow-up in the summary; it enters this change only where the requested behavior depends on it. Verify freely; scratch scripts + quick checks = disposable; committed tests = where the task asks or the repo already keeps tests for that kind of change, sized like neighboring test files (~one focused test per stated behavior). Everywhere: an existing feature's behavior changes for the request, a ruling or a bug fix alone; ambiguous task → the one reading its wording + surrounding code most directly support, assumption stated in the summary; ask only where my intent alone decides between materially different readings; the final message names each change past the request, small ones included, read off the diff.
- Edit tokens scale with bytes emitted → surgical edit over whole-file rewrite wherever both yield the same bytes.
